# ТЗ: агрегатор фундаментальных данных с LLM-разметкой и доставкой в Telegram

## Цель

Система непрерывно собирает новости и первичные данные по трём рынкам
(акции США, крипта, форекс), складывает их в одну базу, размечает через LLM
(привязка к активу + дата применимости), позволяет сопоставить события с
движением цены и отправляет отобранное в Telegram.

## Что НЕ входит в v1

- Торговые сигналы и автоторговля.
- Фронтенд сложнее простого служебного дашборда.
- Оптимизация под низкую задержку. Приоритет — корректность и полнота данных.
- Напоминания по датам применимости. Данные под них собираем, механику не делаем.

## Стек (значения по умолчанию, можно оспорить с обоснованием)

- Python 3.11+
- PostgreSQL. Если развёртывание окажется проблемой — SQLite на старте,
  но схема должна переноситься без переписывания.
- httpx + tenacity для ретраев
- APScheduler или системный cron
- LLM: Gemini (см. отдельный раздел)

## Архитектура

```
collectors → raw store → дедупликация → нормализация →
LLM-разметка → резолв активов → price join → Telegram delivery
```

Каждый коллектор изолирован: падение одного источника не останавливает остальные.

# 1. Источники

Перед началом агент **обязан** проверить актуальные лимиты, формат ответа и
доступность каждого эндпоинта по официальной документации. Сведения ниже могли
устареть. Если что-то не сходится — сообщить, а не подгонять код под текст ТЗ.

## Акции США

- **SEC EDGAR** — официальный API, без ключа. Подачи 8-K (существенные события),
  10-Q, 10-K, Form 4 (инсайдерские сделки). Первоисточник, высший приоритет.
- **Finnhub** — новости по тикерам, календарь отчётностей.
- **Marketaux** — новости с привязкой к тикерам. На бесплатном тарифе отдаёт
  мало статей за запрос, проверить лимит.

## Крипта

- **CryptoPanic API** — агрегатор с голосами сообщества. Лимиты двухуровневые:
  запросы в секунду плюс месячный потолок.
- **cryptocurrency.cv** — бесплатный open-source агрегатор без ключа. Резерв.

## Форекс

- **Экономический календарь**: Financial Modeling Prep (есть бесплатный план)
  или Finnhub. Обязательны поля actual / forecast / previous.
- **RSS и страницы пресс-релизов** ФРС, ЕЦБ, Банка Англии, Банка Японии.
- **FRED API** (бесплатно) — макроряды и доходности гособлигаций.
- **CME FedWatch** — вероятности решений ФРС. Официальный API платный
  (порядка $25/мес). На старте использовать неофициальный пакет `cme-fedwatch`:
  считает по опубликованной методологии CME из публичных данных CME и FRED,
  но хранит только около 5 последних рабочих дней, для бэктеста не подходит.

# 2. Таксономия активов

Два уровня. Каждая новость получает и класс, и конкретику, когда она есть.

**asset_class**: `equity | fx | crypto | commodity | index | rates | macro`

**scope** — насколько широко применима новость:

- `market_wide` — весь класс («акции США падают на данных по инфляции»)
- `group` — сектор, регион, группа («техсектор», «евро против всех»)
- `specific` — конкретный инструмент (AAPL, EUR/USD, BTC)

Одна новость может иметь несколько привязок с разным scope одновременно.
Пример: решение ФРС → (rates, market_wide) + (fx, specific, EUR/USD) +
(equity, market_wide) + (crypto, market_wide).

# 3. Схема БД

## raw_items — сырое, ничего не теряем

```
id, source, source_item_id, url, title, body, published_at (UTC),
fetched_at, raw_json, content_hash
```

## items — дедуплицированное и нормализованное

```
id, canonical_url, title, body, published_at, dedup_group_id
```

## assets — справочник инструментов

```
id            bigserial pk
asset_class   asset_class not null
symbol        text not null        -- AAPL, EURUSD, BTC
name          text
exchange      text                 -- для акций
base_ccy      text                 -- для fx: EUR
quote_ccy     text                 -- для fx: USD
sector        text                 -- для акций
is_active     bool default true
unique (asset_class, symbol)
```

## asset_aliases — распознавание в тексте

```
asset_id   bigint fk assets
alias      text not null      -- "Apple", "эпл", "биткоин", "евродоллар"
lang       text
source     text
unique (alias, lang)
```

Наполнять из справочников бирж плюс вручную. Без алиасов LLM вернёт «Apple»,
в базе будет AAPL, и связь не построится.

## item_assets — привязка новости к активу (ядро системы)

```
id            bigserial pk
item_id       bigint fk items not null
asset_class   asset_class not null
scope         scope not null
asset_id      bigint fk assets null   -- NULL при scope = market_wide/group
group_label   text null               -- "tech", "EM currencies" при scope = group
direction     direction null          -- bullish | bearish | neutral
importance    smallint                -- 1..5, для ЭТОГО актива
confidence    numeric(3,2)
is_primary    bool                    -- главный актив новости или упомянут вскользь
```

Ключевое: **direction и importance живут здесь, а не на уровне новости.**
Одна новость бывает бычьей для одного актива и медвежьей для другого
(укрепление доллара: bearish для EUR/USD, bullish для DXY). Если повесить
направление на новость целиком, эта информация теряется безвозвратно.

## item_relevance — когда новость применима

```
id              bigserial pk
item_id         bigint fk items not null
relevance_type  text not null   -- immediate | scheduled | window | unknown
relevant_from   timestamptz     -- начало применимости (UTC)
relevant_to     timestamptz     -- конец, NULL если точечное событие
date_precision  text            -- exact | day | month | quarter | unknown
raw_phrase      text            -- как было в тексте: "в следующий четверг"
anchor_ts       timestamptz     -- published_at, от которого считали относительную дату
resolved_by     text            -- llm | rule | manual
```

Типы:

- `immediate` — факт уже случился, применимо сразу. relevant_from = published_at.
- `scheduled` — назначенное событие в будущем (заседание ФРС, отчётность,
  экспирация локапа, дата отсечки по дивидендам).
- `window` — применимо в интервале («эффект от пошлин проявится в Q1»).
- `unknown` — дату извлечь не удалось. Не выбрасывать, пометить и оставить.

**Главная ловушка.** Относительные даты («в следующий четверг», «на будущей
неделе») LLM обязана разрешать **от published_at новости, а не от текущей
даты**. published_at передаётся в промпт явно. После ответа код проверяет,
что полученная дата лежит в разумном окне от anchor_ts (от −1 дня до
+18 месяцев). Всё, что вне окна, помечается как unknown и уходит на ручную
проверку, а не пишется в базу как есть. Без этой проверки база тихо
наполнится датами-мусором.

## econ_events — экономический календарь

```
event_name, country, currency, scheduled_at, actual, forecast, previous,
surprise (вычисляемое), importance
```

Forecast ревизуется — хранить снимки, не перезаписывать.

## rate_expectations — ожидания по ставке

```
central_bank, meeting_date, snapshot_at, outcome, probability
```

## annotations — сырой ответ LLM

```
item_id, model, prompt_version, created_at, payload_json,
input_tokens, output_tokens, cost_estimate
```

Сырой JSON хранить всегда, даже когда он уже разобран в таблицы выше. При смене
промпта можно будет переразобрать без повторных вызовов LLM.

## prices — OHLCV по инструментам, для валидации

## deliveries — что уже отправлено в Telegram

```
item_id, channel, sent_at, message_id, status
unique (item_id, channel)
```

## Дедупликация

Одна новость приходит из пяти мест. Группировать по нормализованному URL,
затем по хэшу заголовка, затем по нечёткому совпадению заголовка (порог в
конфиге) в окне ±6 часов. Оригиналы не удалять, помечать через dedup_group_id.

## Время

Всё в UTC в базе, конвертация только на отображении. У каждой записи различать
`published_at` (когда вышло) и `fetched_at` (когда мы узнали). Для бэктеста
использовать только `fetched_at`.

## Индексы под целевые запросы

```sql
create index on item_assets (asset_class, scope);
create index on item_assets (asset_id) where asset_id is not null;
create index on item_relevance (relevant_from);
create index on item_relevance (relevance_type, relevant_from);
```

## Проверочные запросы (должны работать быстро)

1. Все новости по AAPL за период.
2. Всё, что применимо к форексу вообще на завтра.
3. Что ждёт по EUR/USD на ближайшие 14 дней, сортировка по importance.
4. Все события с `relevance_type = 'scheduled'` в будущем. Это готовая основа
   для напоминаний в следующей версии, отдельная таблица под них не нужна.

# 4. LLM-разметка

## Контракт

Вход в промпт обязательно включает: title, body, source, **published_at в ISO**.

Выход:

```json
{
  "assets": [
    {
      "asset_class": "fx",
      "scope": "specific",
      "symbol_or_name": "EUR/USD",
      "group_label": null,
      "direction": "bearish",
      "importance": 4,
      "is_primary": true,
      "confidence": 0.8
    },
    {
      "asset_class": "equity",
      "scope": "market_wide",
      "symbol_or_name": null,
      "group_label": null,
      "direction": "bearish",
      "importance": 2,
      "is_primary": false,
      "confidence": 0.5
    }
  ],
  "relevance": {
    "type": "scheduled",
    "date_iso": "2026-10-28",
    "date_precision": "day",
    "raw_phrase": "на заседании в конце октября"
  },
  "event_type": "earnings | guidance | m_and_a | regulatory | macro | rate_decision | cb_speech | other",
  "summary": "одна строка сути"
}
```

## Резолв активов

LLM возвращает `symbol_or_name` свободным текстом. Отдельный шаг сопоставляет
его с таблицей assets через asset_aliases. Что не сопоставилось — в очередь
`asset_resolution_queue` на ручной разбор. **Не отбрасывать молча**: это
главный источник тихой потери данных. Доля нераспознанных выводится в метрики.

## Требования

- Идемпотентность: повторный прогон того же item с тем же prompt_version не
  создаёт дубль. Версия промпта хранится вместе с результатом.
- Валидация ответа по схеме. При невалидном ответе один повтор, потом
  запись в dead letter.
- Готовым сентиментом от провайдеров новостей не ограничиваться: методологии
  у вендоров разные и оценки несопоставимы между собой. Собственная разметка —
  источник истины.

## Работа с Gemini

- Бесплатный тариф покрывает только модели Flash и Flash-Lite, Pro переведён
  на оплату. Лимиты считаются на проект, а не на ключ, и реальные цифры для
  своего проекта смотреть в AI Studio. Цифры из статей не использовать.
- Первым упирается лимит **запросов в сутки**, поэтому одна запись на один
  вызов не годится. Размечать пачками: один вызов = N новостей, N в конфиге,
  начать с 10. Схема ответа — массив, в каждом элементе явный id для сверки
  с входом.
- Структурированный вывод задавать через responseSchema / JSON-режим, а не
  просьбой в тексте промпта.
- На 429 — экспоненциальная пауза с джиттером, не мгновенный повтор.
  При исчерпании дневного лимита не падать: необработанное в очередь,
  продолжить в следующем окне.
- Логировать токены и оценку стоимости каждого вызова.

## Интерфейс под существующий код

У заказчика есть готовая обвязка Gemini из другого проекта. Спрятать провайдера
за интерфейсом:

```python
class LLMClient(Protocol):
    def annotate_batch(self, items: list[ItemForAnnotation]) -> list[Annotation]: ...
```

Реализация под Gemini — отдельный модуль, подключается через конфиг. Агент
пишет заглушку и тесты против интерфейса, рабочий клиент заказчик отдаст
отдельно. Доменная логика не должна знать, что провайдер — Gemini.

# 5. Логика по форексу

Само решение по ставке рынок не двигает — оно уже в цене. Двигает отклонение
от ожиданий и сдвиг риторики. Реализовать:

1. **Сюрприз по ставке.** Перед заседанием сохранять снимок ожиданий
   (rate_expectations). После решения считать, совпало ли оно с наиболее
   вероятным исходом и насколько.
2. **Диффинг заявлений ЦБ.** Подавать в LLM текущее и предыдущее заявление
   **вместе** и просить: что изменилось в формулировках, в какую сторону
   (ястребиную или голубиную), какие фразы добавлены и убраны. Это даёт больше
   сигнала, чем оценка одного текста.
3. **Выступления членов ЦБ** между заседаниями. Учитывать вес выступающего:
   председатель важнее регионального члена без права голоса. Справочник весов
   в конфиге.
4. **Сюрприз по макро.** Из econ_events считать (actual − forecast), нормировать
   на историческое стандартное отклонение по этому индикатору.
5. **Дифференциал ставок** между странами пары (например, доходности
   двухлетних бумаг США и Германии для EUR/USD) из FRED. Для форекса это часто
   более сильный фундаментальный индикатор, чем сами новости.

# 6. Доставка в Telegram

Отдельный модуль, не внутри коллекторов. Получает на вход уже размеченные
записи, решает, что отправлять, и отправляет.

Требования:

- Сообщение содержит: краткую суть (summary), привязанный актив, дату
  применимости и **ссылку на первоисточник**.
- Фильтры отправки настраиваются в конфиге: по asset_class, по конкретным
  активам, по минимальному importance, по direction. Слать всё подряд нельзя,
  порог обязателен.
- Ничего не отправляется дважды. Проверка по таблице deliveries до отправки,
  запись после успеха.
- Соблюдать лимиты Telegram Bot API, троттлинг очереди отправки.
- Падение Telegram не должно ронять пайплайн и не должно терять записи:
  неотправленное остаётся в очереди и уходит при следующем запуске.
- Токен бота и идентификатор получателя — через переменные окружения.
- Доставка подключается после этапа с LLM-разметкой, раньше отправлять нечего.

Решения, которые агент принимает сам и фиксирует в README: библиотека для
Bot API, формат разметки сообщения, устройство очереди отправки.

Вопрос к заказчику до начала этапа: личный чат или канал, и нужны ли
интерактивные команды (подписка на актив прямо из бота) или только
односторонняя отправка. По умолчанию — односторонняя отправка в один чат.

# 7. Валидация

Обязательная часть, не опциональная.

Джойн событий с ценами: для каждого размеченного события считать движение
инструмента на горизонтах +5м, +1ч, +1д от **fetched_at**.

Отчёт должен отвечать на вопрос: отличается ли распределение движений для
событий с importance 4–5 от событий с importance 1–2, и совпадает ли
предсказанное direction с фактическим знаком движения. Если нет — разметка
бесполезна и промпт надо переделывать.

Никакого lookahead bias: при расчёте использовать только данные, доступные на
момент fetched_at.

# 8. Эксплуатация

- Все ключи через переменные окружения, никаких секретов в репозитории.
  В `.env.example` перечислить все нужные ключи.
- Rate limiting на каждый источник отдельно, с запасом до документированного лимита.
- Структурные логи. Метрики: собрано записей, отброшено дублей, ошибок API,
  доля нераспознанных активов, потрачено на LLM, отправлено в Telegram.
- `docker-compose.yml` для локального запуска.
- README: как получить каждый ключ, как запустить, как добавить новый источник.

# 9. Этапы

Сдавать по одному, не всё сразу.

**Этап 1.** Схема БД, каркас коллектора, два источника: SEC EDGAR плюс один
новостной. Дедупликация.
*Приёмка:* сутки непрерывной работы без падений, дубли корректно схлопываются.

**Этап 2.** Остальные источники, включая календарь и RSS центробанков.
*Приёмка:* все три рынка покрыты, коллекторы изолированы друг от друга.

**Этап 3.** LLM-разметка: привязка к активам, даты применимости, резолв
через алиасы, версионирование промптов, учёт стоимости.
*Приёмка:* 100 записей размечены, ручная проверка выборки из 20 показывает
осмысленный результат; проверочные запросы из раздела 3 отрабатывают.

**Этап 4.** Доставка в Telegram.
*Приёмка:* сообщения приходят, повторов нет, фильтры работают, падение
Telegram не теряет записи.

**Этап 5.** Сбор цен и отчёт по валидации.
*Приёмка:* отчёт построен, вывод о полезности разметки сформулирован явно.

**Этап 6.** Логика по форексу: сюрпризы, диффинг заявлений, дифференциал ставок.

# 10. Правила для агента

- Перед началом проверить актуальность лимитов и форматов ответов всех API.
  Расхождение с ТЗ — повод сообщить, а не подогнать код под текст.
- На каждом этапе тесты: как минимум на дедупликацию, парсинг ответов
  источников, резолв активов, разрешение относительных дат и валидацию
  LLM-вывода.
- Не изобретать собственную сентимент-модель, использовать LLM по контракту
  из раздела 4.
- Если для нужного эндпоинта требуется платная подписка — остановиться
  и спросить, а не встраивать платный тариф молча.
