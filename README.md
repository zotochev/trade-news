# trade-news

Сборщик фундаментальных данных по акциям США, крипте и форексу. Размечает новости через LLM
и отправляет отобранное в Telegram. Техническое задание: [tz-news-aggregator.md](tz-news-aggregator.md).

**Статус:** этапы 1 (сбор, дедупликация), 3 (LLM-разметка), 4 (рассылка в Telegram) и админка. План в [TODO.md](TODO.md).

## Быстрый старт

```bash
uv sync
cp .env.example .env              # заполнить ключи, см. ниже
uv run trade-news db-upgrade      # создать или обновить схему (миграции Alembic)
uv run trade-news sources         # какие источники есть и каких ключей не хватает
uv run trade-news collect         # один проход по всем включённым источникам
uv run trade-news collect sec_edgar
uv run trade-news run             # работа по расписанию (блокирующий режим)
uv run trade-news stats --hours 24
```

Флаг `--pretty` выводит логи в читаемом виде вместо JSON.

`.env`, `config.yaml` и `data/` ищутся в текущей рабочей папке.

Тесты: `uv run pytest`. Линтер: `uv run ruff check . && uv run ruff format --check .`

## Запуск на сервере (systemd)

Юнит: `trade-news.service`. Перед стартом он применяет миграции (`ExecStartPre=... db-upgrade`),
затем запускает `trade-news run`.

1. Склонировать репозиторий в `/opt/trade-news`, выполнить `uv sync --no-dev`, создать `.env`
   по образцу `.env.example`.
2. В юните указан `User=crip`. Если сервис будет работать под другим пользователем, поправить
   `User=`. Если путь не `/opt/trade-news`, поправить `WorkingDirectory=` и `ExecStart*=`.
   Пользователь должен иметь право на запись в `/opt/trade-news/data`.
3. Установить и запустить:
   ```
   sudo cp trade-news.service /etc/systemd/system/
   sudo systemctl daemon-reload
   sudo systemctl enable --now trade-news
   ```
4. Логи: `journalctl -u trade-news -f`. Логи в JSON, удобно фильтровать через `jq`.
   Статистика: `cd /opt/trade-news && .venv/bin/trade-news stats`.

Остановка корректная. `systemctl stop` шлёт SIGTERM, и планировщик ждёт, пока текущие сборщики
допишут свою транзакцию: EDGAR иногда отвечает 20–30 секунд, поэтому `TimeoutStopSec=120`.
Запуски, оборванные убийством процесса, при следующем старте помечаются в `collector_runs`
как `aborted`. После падения сервис перезапускается сам (`Restart=on-failure`).

## Ключи

Все секреты задаются только через переменные окружения (`.env`). Полный список в `.env.example`.

| Переменная | Где получить |
|---|---|
| `SEC_USER_AGENT` | Ключ не нужен. SEC требует User-Agent вида `Name email@domain` ([fair access](https://www.sec.gov/os/accessing-edgar-data)) |
| `FINNHUB_API_KEY` | Бесплатная регистрация на https://finnhub.io/register, ключ появится в дашборде |
| `MARKETAUX_API_KEY` | https://www.marketaux.com/register (бесплатно 100 запросов в сутки) |
| `FRED_API_KEY` | Аккаунт на https://fredaccount.stlouisfed.org, ключ на https://fredaccount.stlouisfed.org/apikeys. Нужен FRED и календарю |
| `GEMINI_API_KEY` | https://aistudio.google.com/app/apikey (нужен с этапа 3) |
| `TELEGRAM_BOT_TOKEN` | @BotFather → `/newbot`. Нужен **отдельный** бот, см. раздел Telegram |
| `TELEGRAM_CHAT_ID` | Ваш chat id (владелец). Его можно узнать у @userinfobot |

Источник, которому не хватает ключа, пропускается с предупреждением в логе. Остальные продолжают работать.

## Telegram: подписка

Бот запускается внутри `trade-news run` отдельным потоком, если задан `TELEGRAM_BOT_TOKEN`.

| Команда | Что делает |
|---|---|
| `/start` | подписывает чат сразу, без подтверждения; работает в личке и в группе (`/start@bot`) |
| `/stop` | отписывает |
| `/help` | описание бота и статус подписки |
| `/sources` | какие источники слушает бот: последний сбор, ошибка ли, сколько новых записей за 24 ч |

- **Каналы.** В канале нельзя отправить `/start`, поэтому канал подписывается, когда бота
  добавляют в него администратором.
- **Блокировка.** Если бота заблокировали или удалили из группы, чат отписывается автоматически.
- **Владелец** (`TELEGRAM_CHAT_ID`) получает рассылку всегда, даже без подписки, и видит
  уведомление, когда кто-то подписался или отписался. Других ролей нет.
- **Хранение.** Подписчики лежат в таблице `subscribers`. При отписке строка не удаляется,
  только деактивируется. Список: `trade-news subscribers`.

**Нужен отдельный бот.** Telegram разрешает только одному процессу опрашивать `getUpdates`
на один токен, второй получает 409 Conflict. Если дать trade-news токен бота ict-monitor,
приложения начнут перехватывать команды друг у друга. При конфликте в логе появляется
`telegram_polling_conflict`.

### Рассылка (этап 4)

Правила задаются на странице админки «Подписчики и рассылка» и хранятся в таблице `settings`.
**По умолчанию рассылка выключена.** Рядом с каждым порогом видно, сколько новостей
за последние 24 часа прошло бы. «Проверить» считает предпросмотр по введённым значениям,
ничего не сохраняя.

- Новость проходит, если её главный актив (primary с наибольшей importance) удовлетворяет
  правилам: минимальная importance, направление не нейтральное, тип события, класс актива.
  Или если любой из её активов входит в «мои активы» и набирает свой, отдельный порог.
- Получатели: владелец `TELEGRAM_CHAT_ID` плюс активные подписчики.
- Без повторов: на каждую пару (новость, чат) заводится строка в `deliveries`
  (pending → sent | failed | skipped). Она проверяется до отправки и обновляется после.
- Лимиты: не больше N сообщений в час на чат, остальные ждут. Новости старше
  `max_age_hours` не отправляются никогда. Отправка идёт не быстрее 20 сообщений в секунду
  в целом и около одного в секунду в один чат (лимиты Bot API).
- Если Telegram недоступен, строки остаются `pending` и уходят при следующем запуске
  (задача запускается раз в минуту). Если бот заблокирован, чат отписывается. На ошибку
  разметки HTML сообщение отправляется ещё раз обычным текстом.
- Формат сообщения (`trade_news/telegram/message.py`): главный актив со стрелкой и важностью,
  краткая суть, другие активы, дата применимости, ссылка на первоисточник.

## Сделки инсайдеров (Form 4)

Каждую новую Form 4 коллектор EDGAR скачивает целиком (`<accession>.txt`, один запрос)
и разбирает XML: тикер, кто совершил сделку (роль), код сделки, количество, цена, флаг плана
10b5-1 (`trade_news/collectors/form4.py`). Смысл несут только сделки на рынке: P — покупка,
S — продажа. Гранты, исполнение опционов, удержание налога и подарки — шум.

В LLM уходят только значимые подачи. Пороги задаются в `config.yaml → sources.sec_edgar.params.form4_thresholds`:
покупка от $100K, продажа от $1M, продажи по плану 10b5-1 отбрасываются. Из инсайдеров
учитываются только CFO (`cfo_only`): копирование их сделок исторически даёт ~19.5% годовых
против ~14–16% у CEO и членов совета и ~9% у владельцев 10%. CFO определяется по должности
(`CFO`, `Chief/Principal Financial Officer`, `PFO`); главный бухгалтер (CAO) не в счёт. Остальные подачи
сохраняются с пометкой `llm_skip` и причиной. Заголовок и текст новости собираются из фактов:
`Form 4 · ETRA · Director buys $20.0M`. Промпт v2 содержит правила для инсайдеров: крупная
покупка CEO/CFO или от $1M → importance 4–5. Одна и та же сделка из нескольких подач
склеивается по точному совпадению заголовка.

## Доли больше 5% (Schedule 13D)

Коллектор EDGAR читает и ленту `SCHEDULE 13D` (поправки 13D/A идут с ней): владелец более 5%
с намерением влиять на компанию. С 2024 года подача — структурированный XML, коллектор
скачивает только `primary_doc.xml` (~10–30 КБ, без приложений) и разбирает его
(`trade_news/collectors/schedule13d.py`): эмитент, участники с долей и числом акций, дата
события, источник денег, цель (Item 4), недавние сделки. Подачи с долей 5–50% идут во
второй проход «кита»; цифры доли берутся из подачи, доля «до» — из предыдущей 13D того же
владельца в нашей базе, снижение доли «китом» не считается. Разобранные подачи (Form 4 и 13D)
не отправляются повторно (accession в курсоре), первая страница новой формы помечается
`first run backlog` и в LLM не идёт. 13G (пассивные инвесторы) не собираем.

## Разблокировки токенов

Доли команды и ранних инвесторов в криптопроектах выдаются по графику, опубликованному при
запуске токена (обычно год ничего, потом крупная разовая выдача и порции раз в месяц/квартал).
Коллектор `token_unlocks` (`trade_news/collectors/token_unlocks.py`) берёт графики DefiLlama без
ключа: список проектов (~370) и файл каждого проекта (до ~17 МБ). Файлы разбираются потоком
(ijson): из них берутся только уже разблокированный объём и разовые выдачи (cliff), пик памяти
~75 МБ. Общий файл `emissionsIndex` (22 МБ) намеренно не используется — целиком он съедает
слишком много памяти. За запуск обновляется `per_run` проектов по кругу (3 раза в 30 минут —
полный круг за ~2,5 дня).

Выдачи от `min_pct` (1%) уже разблокированного объёма ложатся в таблицу `token_unlocks` и на
страницу «Рынок» админки. Выдачи казне/резервам (`noncirculating`) не считаются. За `lead_days`
(3 дня) до выдачи, если по текущей цене (coins.llama.fi) она от `min_usd` ($5M), создаётся
новость `Token unlock · ARB · 92,645,833 tokens ($18.0M, 1.3% of unlocked supply) on 2026-10-15`.
Источник в `always_sources` доставки: пороги уже применил коллектор.

## Календарь вынужденных потоков

Даты, когда кто-то **обязан** купить или продать по правилу, марже, календарю или мандату
(задание: `docs/tasks/forced-flows.md`). Хранятся в `calendar_events` отдельно от новостей,
пишутся по ключу (`type|date|...`): повторный запуск обновляет, а не дублирует; правка в
админке помечает событие `edited`, и коллектор его больше не трогает.

| Тип | Откуда | Кто вынужден |
|---|---|---|
| `opex_monthly`, `opex_quarterly` | правило: 3-я пятница (праздник → четверг) | маркетмейкеры снимают хеджи; квартальная — с ребалансировкой S&P 500 (декабрь — и Nasdaq-100) |
| `vix_expiry` | правило Cboe: среда за 30 дней до 3-й пятницы след. месяца | хеджи волатильности |
| `month_end`, `quarter_end` | последний рабочий день NYSE | ребалансировка фондов, хедж валюты |
| `index_rebalance` | MSCI: последний рабочий день февраля/мая/августа/ноября | пассивные фонды |
| `russell_recon` | 4-я пятница июня, 2-я пятница декабря (с 2026 — дважды в год) | фонды малых компаний |
| `index_change` | ручной ввод в админке | индексные фонды по конкретным бумагам |
| `earnings`, `buyback_blackout` | Finnhub, ~70 крупнейших (`finnhub_calendar.symbols`); окно — 28 дней до отчёта | компании не выкупают свои акции |
| `ipo_lockup` | Finnhub IPO от $100M, IPO + 180 дней (оценка) | инсайдеры получают право продавать |
| `ust_auction` | TreasuryDirect, ноты и бонды (~10 дней вперёд); крупные — от 10 лет и refunding | первичные дилеры |
| `token_unlock` | таблица `token_unlocks` (коллектор разлоков); крупные — от 5% | получатели токенов |
| `cb_meeting` | FedWatch (ФРС на год вперёд), ForexFactory (решения по ставке на неделе) | пересчёт позиций |
| `btc_halving` | mempool.space: высота блока, 10 минут на блок (оценка) | майнеры |
| `ru_minfin_announce` | 3-й рабочий день по производственному календарю (isdayoff.ru) | Минфин задаёт покупки/продажи валюты |
| `ru_tax_period` | 28-е число (выходной → следующий рабочий) | экспортёры продают валюту |
| `ru_minfin_ops` | коллектор `ru_minfin`: сообщение о месячных операциях из лент ТАСС/РИА/Ведомостей + зеркалирование ЦБ из config | Минфин и ЦБ покупают/продают валюту каждый день периода |
| `ru_dividend_cutoff` | smart-lab.ru (дивидендный календарь) + состав IMOEX из ISS; крупные — доходность от 7% или вес от 3% | дивидендные фонды, гэп после отсечки |
| `ru_fx_rule` | ручной ввод в админке | экспортёры: норма обязательной продажи валютной выручки |

Коллекторы: `flow_rules` (расчёт на 365 дней), `finnhub_calendar`, `treasury_auctions` — раз в
6 часов. Чтение: `trade_news/flows/calendar.py` (подмешивает разлоки и заседания ЦБ).

- **API:** `GET /api/calendar?from=YYYY-MM-DD&to=YYYY-MM-DD&types=a,b&markets=crypto,ru&major=true`
  — по умолчанию сегодня + 30 дней. Снаружи API закрыт basic auth nginx; дашборд на этом же
  сервере ходит напрямую: `http://127.0.0.1:10000/api/calendar`.
- **Telegram:** в понедельник (`flows.digest_hour_utc`, 05:00 UTC = 08:00 МСК) — дайджест недели
  по дням; каждый день в 15:00 UTC — напоминание о крупных событиях следующего рабочего дня (в
  пятницу — до понедельника), каждое один раз. Проверка без отправки:
  `trade-news flows digest --dry-run`, `trade-news flows remind --dry-run`.
- **Админка → «Календарь»:** 2–8 недель с фильтрами, ручное добавление и правка.

## Плечо в крипте (история)

Биржи бесплатно отдают только текущие значения (Binance — ещё 30 дней), поэтому историю копим
сами (часть B задания `docs/tasks/forced-flows.md`). Ценность — длинный ряд: таблицы очисткой
не трогаются. Оповещений пока нет («риск каскада» — позже).

- **Снимки раз в 5 минут** (коллектор `crypto_leverage`, таблица `crypto_derivs`): открытый
  интерес (USD и монеты), ставка фандинга с её интервалом, соотношение лонгов и шортов по
  аккаунтам, цена — по Binance, Bybit, OKX. Монеты: BTC, ETH + 10 крупнейших по открытому
  интересу (рейтинг Bybit раз в сутки; золото и стейблкоины исключены, `exclude`). ~40
  запросов за запуск, ~10 тыс. строк в сутки (~2 МБ).
- **Ликвидации** (`trade_news/crypto/liquidations.py`, таблица `crypto_liquidations`):
  websocket-потоки трёх бирж в отдельных потоках внутри `run`, суммы в USD по минутам, монете,
  бирже и стороне (`long` — принудительно закрыты лонги, это продажи). Монеты вне списка —
  в `OTHER`. Ограничения: Binance присылает не больше одной ликвидации на монету в секунду
  (в каскаде занижает); Bybit — только по отслеживаемым монетам; OKX — полный поток.
  Включение: `crypto.liquidations` в `config.yaml`.
- **История Binance за 29 дней** (открытый интерес и лонги/шорты, 5 минут; фандинг пустой):
  `trade-news crypto-backfill` — один раз, повторный запуск ничего не дублирует.
- **API:** `GET /api/crypto/leverage?asset=BTC&from=…&to=…&exchange=` (по умолчанию последние
  24 ч, максимум 92 дня): снимки по биржам с фандингом, приведённым к 8 часам (`funding_8h`),
  итоги по всем биржам на каждый снимок (сумма открытого интереса, фандинг взвешенный по нему)
  и ликвидации по минутам. `asset=OTHER` — ликвидации вне списка монет.

## Россия: Минфин, дивиденды, позиции во фьючерсах

Часть C задания `docs/tasks/forced-flows.md`.

- **Операции Минфина** (`ru_minfin`): minfin.gov.ru закрыт для зарубежных IP (503 «Доступ
  временно ограничен»), поэтому месячное сообщение (3-й рабочий день, ~15:30 МСК) берётся из
  лент ТАСС, РИА и «Ведомостей». Коллектор опрашивает их раз в 10 минут только 3 дня от дня
  анонса и останавливается, как только месяц найден. Из текста извлекаются направление, объём
  в день (или общий объём, делённый на рабочие дни периода) и период. К нему прибавляется
  зеркалирование ЦБ — `ru_minfin.cbr_mirroring_rub_bn_day` в `config.yaml`, ЦБ объявляет его
  дважды в год (**обновлять в январе и июле**). Результат: событие `ru_minfin_ops` в календаре
  и сообщение в Telegram сразу (источник в `always_sources`).
- **Дивидендные отсечки** (`moex_dividends`): бесплатных дивидендов в ISS больше нет (только
  платный CCI), даты берутся из календаря smart-lab.ru, бумаги — только из индекса Мосбиржи.
  Событие — последний день покупки с дивидендом.
- **Открытые позиции физлиц и юрлиц** (`moex_open_positions`, таблица `moex_open_positions`):
  ISS `statistics/engines/futures/markets/forts/openpositions/<актив>`, Si, RTS, CNY, раз в
  час последние 5 дней; заодно каждый запуск дозагружает 30 дней истории назад, до 2021 года.
  **API:** `GET /api/ru/open-positions?asset=Si&from=YYYY-MM-DD&to=YYYY-MM-DD` — по дням
  `individuals` и `legal`: лонги, шорты, нетто (контракты), число держателей, изменение за день.
- **Норма продажи валютной выручки** — тип `ru_fx_rule`, вводится вручную на странице
  «Календарь».

## Потоки в ETF и запасы компаний

Часть D (запрос дашборда economy-model-lab, 2026-10-15).

- **Потоки в спотовые биткоин- и эфир-ETF США** (`etf_flows`, таблица `etf_flows`): Farside,
  вся история одной таблицей (BTC с 11.01.2024, ETH с 23.07.2024), чистый поток в млн $ по
  каждому фонду и дню. Cloudflare отдаёт 403 / «Just a moment» на небраузерный User-Agent,
  поэтому коллектор представляется Chrome; если закроют и его — коллектор падает с понятной
  ошибкой (запасной путь, не сделан: паи × NAV с сайтов эмитентов). Раз в 3 часа страницы
  перечитываются целиком и записываются поверх: Farside дозаполняет день на следующее утро и
  правит поздние отчёты.
  **API:** `GET /api/etf/flows?asset=BTC|ETH&from=YYYY-MM-DD&to=YYYY-MM-DD` (по умолчанию 90
  дней) → `flows` [{date, fund, flow_usd_m}] и `totals` [{date, flow_usd_m, funds}].
- **Запасы BTC и ETH у публичных компаний** (`crypto_treasuries`, таблица `crypto_treasuries`):
  CoinGecko без ключа, историю не хранит — копим сами, снимок в сутки (Strategy/MSTR и др.).
  **API:** `GET /api/treasuries?coin=BTC&company=MSTR&from=&to=` — без `from` последний снимок
  всех компаний.

## LLM-разметка (этап 3)

Задача `annotate` внутри `trade-news run` каждые `llm.interval_seconds` берёт свежие записи
и отправляет их в LLM пачками по `llm.batch_size`. Берутся только записи не старше
`llm.max_item_age_hours`, по одной на группу дублей, кроме исключённых в `llm.exclude`
(по умолчанию пусто; мелкие Form 4 отсеивает сам коллектор). Контракт ответа из раздела 4 ТЗ лежит в `trade_news/annotation/contract.py`
(pydantic). Из него же генерируется JSON Schema для провайдера.

- **Провайдер** за протоколом `LLMClient.annotate_batch`, реализация Gemini в `trade_news/llm/gemini.py`.
  Используются только модели из `llm.models`, по порядку. Каждый вызов пишется в `llm_calls`:
  токены, оценка стоимости по ценам платного тарифа и статус. Из этой же таблицы считается
  локальная квота, поэтому после рестарта счётчики не обнуляются. 429 «в минуту» — пауза и повтор,
  429 «в день» — переход к следующей модели. Если квоты нет ни у одной модели, записи ждут следующего окна.
- **Идемпотентность:** одна разметка на пару (запись, `PROMPT_VERSION`). После смены промпта
  нужно поднять версию, старые результаты останутся для сравнения. Сырой ответ LLM хранится в
  `annotations.payload_json`.
- **Невалидный ответ** получает один повтор, после второй неудачи запись уходит в `annotation_dead_letters`.
- **Даты.** Относительные даты считаются от `published_at`. Код проверяет результат двумя способами:
  окно «−1 день … +18 месяцев» и собственный разбор фраз вроде «next Thursday», «завтра»,
  «в пятницу». Если дата модели противоречит правилу, берётся дата правила. Всё подозрительное
  помечается `needs_review`.
- **Активы.** Справочник собирается из `trade_news/annotation/assets.yaml` (FX, крипта, индексы,
  сырьё, ставки, русские алиасы) и из SEC `company_tickers.json` (~10 тыс. акций с CIK). Для подач
  EDGAR тикер определяется по CIK и передаётся модели подсказкой. Если актив не нашёлся, он
  попадает в `asset_resolution_queue`, а доля таких видна в `trade-news stats`.

Команды: `trade-news annotate [--batches N]`, `trade-news review -n 20` (выборка для ручной
проверки), `trade-news query asset-news AAPL | class-day fx --date tomorrow | upcoming EURUSD
--days 14 | scheduled` (проверочные запросы раздела 3), `trade-news assets-seed`.

## Секторы и отрасли

Своя двухуровневая классификация по образцу GICS/Morningstar: `trade_news/sectors.py`
(11 секторов, крипта по DACS, валюты с метками «сырьевая»/«защитная»). Отрасль акции
выводится из SIC-кода SEC (`https://data.sec.gov/submissions/CIK##########.json`) с

спрашивает SEC о компаниях, уже встречавшихся в новостях (до `sectors.batch` запросов,
общий лимит `rate_limits.sec`), и пересчитывает сектор крипты, валют и уже известных акций
по справочнику: правка таблицы SIC применяется без новых запросов. Вручную:
`trade-news sectors [--all]`.

## Фон рынка

Сейчас выключен (`background_digest.enabled: false`, 2026-10-07); код и настройки на месте.

Новости ниже порога рассылки не теряются: в `background_digest.hours_utc` (13, 17, 21 UTC)
всем получателям уходит дайджест «Фон рынка» — новости, впервые размеченные с прошлого

## API

Только чтение, внутри процесса админки по префиксу `/api` (`trade_news/api.py`):
- `GET /api/news` — размеченные новости, новые сверху. Фильтры: `since`, `until` (UTC),

  приходят новые записи);
- `GET /api/news/{id}`, `GET /api/sectors`;
- документация OpenAPI: `/api/docs`, `/api/openapi.json`.

Отдаётся наша разметка, заголовок источника и ссылка на первоисточник, без текста из лент
(бесплатные API новостей не разрешают перераспространение). Доступ — basic auth в nginx со
своим файлом паролей, см. `deploy/HTTPS.md`.

## Хранение и очистка

Ежедневная задача (и команда `trade-news cleanup`) удаляет целые группы дублей:
неразмеченные через `retention.unannotated_days` (30), размеченные через
`retention.annotated_days` (365). Сырые строки без ссылок и служебные журналы удаляются через
`retention.logs_days` (90). SQLite переиспользует освободившиеся страницы, так что файл перестаёт расти.

## Как это устроено

```
collector (функция) → Batch(items, cursor) → raw_items → items + dedup_group_id
```

- **Коллектор** — чистая функция `fetch(ctx, cursor) -> Batch`. В базу он не ходит:
  получает свой прошлый курсор и возвращает записи и новый курсор. Пайплайн пишет их
  одной транзакцией. Поэтому после сбоя ничего не теряется и ничего не пропускается.
- **Изоляция.** Каждый источник — отдельная задача APScheduler в своём потоке. Исключение
  логируется и пишется в `collector_runs` со статусом `error`. Остальные источники это не задевает.
- **Лимиты запросов.** Лимиты именованные (`rate_limits` в `config.yaml`), несколько источников
  могут делить один. Например, все запросы к SEC идут через ключ `sec`. Ретраи через tenacity:
  экспоненциальная пауза с джиттером на 429, 5xx и сетевые ошибки. `Retry-After` учитывается.
- **Сырьё не теряется.** `raw_items` уникален по `(source, source_item_id, content_hash)`.
  Повторная выборка ничего не дублирует, а изменённая ревизия той же новости сохраняется отдельной строкой.
- **Время.** В БД всё хранится в UTC. Тип `UTCDateTime` не принимает naive datetime.
  Для бэктеста используется `fetched_at`.

### Дедупликация

Новая запись сравнивается с записями в окне ±`dedup.window_hours` от её `published_at`.
Проверки идут по порядку:

1. нормализованный URL: без `www`, utm- и других трекинговых параметров, фрагмента,
   завершающего слеша, с отсортированным query;
2. точный хэш нормализованного заголовка;
3. нечёткое совпадение заголовка: rapidfuzz `token_sort_ratio` ≥ `dedup.fuzzy_threshold`,
   заголовки короче `dedup.min_title_len` не сравниваются.

Оригиналы не удаляются. Дубликат получает `dedup_group_id`, равный id первой записи группы,
а в `dedup_reason` пишется причина: `url`, `title_hash` или `fuzzy`.

Источники с шаблонными заголовками (EDGAR: `8-K - Apple Inc. (...)`) регистрируются
с `title_dedup=False`. Они дедуплицируются только по id и URL и не участвуют в сравнении
заголовков, иначе две разные подачи одной компании склеились бы.

### SQLite → PostgreSQL

Схема (`trade_news/db/schema.py`, SQLAlchemy Core) переносима. Enum хранятся как text с CHECK,
JSON на PostgreSQL становится JSONB, bigint-ключи на SQLite становятся INTEGER, частичный индекс
объявлен для обоих диалектов. Для перехода достаточно
`DATABASE_URL=postgresql+psycopg://...`, установить `psycopg[binary]` и выполнить
`trade-news db-upgrade`. На SQLite включены WAL и `busy_timeout`. Все записи идут через одну
блокировку процесса, потому что у SQLite один писатель.

Новая миграция после изменения схемы:
`uv run alembic revision --autogenerate -m "..."`. Сгенерированный файл нужно проверить глазами.

## Как добавить источник

1. Создать `trade_news/collectors/<name>.py`:

   ```python
   from trade_news.collectors.base import Batch, Context, RawItem, collector


   @collector("my_source", secrets=("MY_API_KEY",), description="Example: news about X")
   def fetch(ctx: Context, cursor: dict | None) -> Batch:
       resp = ctx.get(
           "https://api.example.com/news",
           params={"since": (cursor or {}).get("since")},
           headers={"Authorization": ctx.secrets["MY_API_KEY"]},
       )
       items = [
           RawItem(
               source_item_id=str(n["id"]),
               title=n["title"],
               body=n.get("text"),
               url=n["url"],
               published_at=...,
               raw=n,
           )
           for n in resp.json()
       ]
       return Batch(items, cursor={"since": ...})
   ```

   `description` показывается в команде бота `/sources`. `ctx.get` уже учитывает лимит и делает ретраи. `ctx.params` берётся из `config.yaml`,
   `ctx.secrets` содержит только объявленные переменные окружения. `published_at` должен быть tz-aware.
2. Добавить секцию в `config.yaml` → `sources.my_source` (`interval_seconds`, `rate_limit`, `params`)
   и при необходимости лимит в `rate_limits`.
3. Добавить ключ в `.env.example`.
4. Написать тест парсинга на сохранённом реальном ответе (`tests/fixtures/`) с фейковым `ctx.get`.
   Примеры в `tests/test_sec_edgar.py`.

Модули из `trade_news/collectors/` импортируются автоматически, регистрировать их где-то ещё не нужно.

## Источники этапа 1 и проверка документации

Проверено 2026-09-23 по официальной документации и живым запросам.

- **SEC EDGAR**, Atom-лента `browse-edgar?action=getcurrent`. Не больше 10 запросов в секунду
  на пользователя суммарно со всех машин, у нас стоит 5. User-Agent обязателен.
  Отличие от ожиданий: параметр `type` фильтрует **по префиксу**. `type=4` возвращает
  в основном 424B2, 485BPOS и т.п., поэтому формы отфильтровываются точно (`4` и `4/A`).
  Form 4 приходит двумя записями (Issuer и Reporting) с одним accession, мы оставляем Issuer.
  Лента иногда отвечает 10–20 секунд, это задержка на стороне SEC.
- **Finnhub**: `/news?category=…&minId=` для инкрементальной выборки и `/company-news` по списку
  тикеров. Бесплатный план: 60 запросов в минуту, у нас стоит 45. `/company-news` отдаёт
  историю за год и только по компаниям Северной Америки. Ключ передаётся заголовком
  `X-Finnhub-Token`, чтобы не попадал в URL и логи.

## Решения, зафиксированные по ходу

- SQLite вместо PostgreSQL на старте, схема переносима (см. выше).
- Запуск через systemd, а не через docker-compose (ТЗ, раздел 8), по решению заказчика.
- Telegram (ТЗ, раздел 6): интерактивная подписка `/start` и `/stop` без подтверждения и без ролей,
  владелец `TELEGRAM_CHAT_ID` получает рассылку всегда. Библиотеку для Bot API не брал:
  нужны три метода, они сделаны на httpx (`trade_news/telegram/api.py`).
- Сроки хранения (ТЗ: «ничего не теряем»): по решению заказчика старые данные удаляются, см. «Хранение и очистка».
- Контракт LLM дополнен: `event_type` включает `insider`, в `relevance` есть `date_to_iso` для окон.
- Gemini: только `gemini-3.5-flash-lite` и `gemini-3.1-flash-lite`. Лимиты в `config.yaml → llm`
  это доля trade-news в квоте проекта, квота уже поделена между приложениями.
